# ADP WDR、Projection、Transaction 与 Repair Protocol 1.0.0

本文件是 `ARCHITECTURE-SPINE.md` 固定的规范性附件。只有全大写关键字 MUST、MUST NOT、SHOULD 才具有 BCP 14（RFC 2119 与 RFC 8174）定义的规范性含义。

## 1. Wire identity、ordering 与 legacy ingress

- identity、fingerprint、batch 和 token binding 使用 RFC 8785 JCS。新 v2 contract字段以schema限制为整数；为无损承载pinned Panel v1，nested brownfield payload可按其pinned schema使用有限IEEE-754小数。canonicalizer必须按ECMAScript number serialization输出小数与`-0 -> 0`，拒绝NaN/Infinity、lone surrogate及绝对值大于`2^53-1`的整数。hash 是 `sha256:` 加 64 位小写十六进制。identity移除其自身identity字段后取JCS hash；只有下文明确列出的capability record双identity preimage例外，不存在其它隐式排除字段。
- 每个 command、projection envelope、audit、state、proof 和 receipt MUST 携带 `contract`，但两个已冻结的brownfield ingress格式除外：`action-flow-index/1.0.0`保持生产中的无envelope relation shape，`conformance-result/1.0.0`保持外部签名格式；二者只能由registry的exact contract record和loaded raw schema选择，不得凭payload自报版本。其它ingress可在双方registry中选择最高共同SemVer，但一旦选择contract，validator必须在任何shape parsing前，以raw schema/registry bytes和registry record重建exact `schema_id|schema_sha256|registry_sha256`，并递归检查document内每个嵌套`contract`。fake anchor、任一raw hash不同、registry record不唯一或嵌套引用不属于已加载registry均返回 `CONTRACT_NEGOTIATION_FAILED`；schema仅验证hash-shaped字符串不能替代该步骤。
- RFC 8785 不排序 array。registry `canonical_array_ordering` 固定可由 RFC 6901 直接定位的结构数组，并用`key_types`逐列声明`string|integer`；`identity_set_fields`固定通配路径下的权限、repair和receipt语义集合。字符串必须已是NFC并按UTF-8 bytes比较，integer按数值比较，tuple逐列比较，null排在非null前。`apply_order`因此是数值`0..n-1`，不得按`"10" < "2"`处理。identity计算前必须按对应registry规则排序，identity key重复（无论值相同或冲突）均拒绝；未注册array只有在本协议明确声明顺序有语义时才保留输入顺序。
- capability的`allowed_operations|allowed_fields|allowed_sections`、repair的`authorization_scopes|finding_ids|action_ids`以及action delta的`changed_fields|evidence_fingerprints`都按`identity_set_fields`的UTF-8总序。identity-set中的每个stored scalar本身必须已经是NFC；validator还必须以NFC后的key检测碰撞，原值不同但normalized key相同也拒绝。meeting board内`items`保留producer的议程/优先级顺序且`item_id`不得重复。其它payload集合按registry规则排序。
- JSON Pointer 一律使用 RFC 6901；空字符串 `""` 表示 document root，`/` 表示名称为空的成员。binding source/target 在 merge 前按 RFC 6901 解引用，missing、duplicate 或越界返回 `PANEL_BINDING_INVALID`。
- meeting/status v1 只按 pinned grammar 解析。meeting `started_at` 必须是带时区 RFC 3339：解析为 instant、转 UTC、向下截到整秒、输出 `YYYY-MM-DDTHH:MM:SSZ`；无 started_at 时才使用 `date + T00:00:00Z`。无时区、leap second、非法日期或两者皆缺返回 `LEGACY_EVIDENCE_TIMESTAMP_REQUIRED`。status v1 必须由调用者提供同样 canonical 的 immutable `observed_at`，不得使用 mtime 或当前时间。
- status v1 alias precedence：ID `action_id > id`，action `action > text > next_action`，due `due_or_trigger > due > trigger`，routing scope `workstream > workstream_id`，affected list `affected_workstreams > affectedWorkstreams > impacts`。`program` 只允许作为 action `routing_scope_id`，WDR command仍必须是 physical `workstream_id`。patch只复制 raw payload 实际出现的字段；decoder default不得变成 mutation。
- create action MUST 携带 exact `action_id`。显式合法 ID优先；否则 producer使用 `ACT-` 加 `SHA-256(JCS({source_fingerprint,source_path,observed_at,routing_scope_id,action,due_trigger}))` 前20位大写 hex。碰撞但 command fingerprint不同返回 `ACTION_ID_COLLISION`，不得探测下一个序号。legacy command ID 是 `legacy:` 加 adapter/version、source artifact/raw hash、root/path、canonical observed_at 和 target ID 的 JCS SHA-256。
- pinned meeting v1的 `wdr_update` 只有free text，不包含target field或collection mode。adapter MUST只把它映射为Meeting Sync History/evidence；不得猜测`progress|blockers|risks|dependencies`。只有输入中存在schema-valid additive typed status payload时才生成status intent，否则返回gap `LEGACY_STATUS_INTENT_REQUIRED`，history仍可提交。相同free text在所有实现中都必须产生零个current-field mutation。

## 2. Ownership、status intent 与 capability

- status-sync 是 action ledger、action-flow、全部 WDR current fields及 `Roadmap` 的唯一 semantic writer。meeting-sync、checkpoint-sync、risk review对这些字段只可生成 `status-mutation-intent/1.0.0`；status-sync验证 evidence、precedence 与 CAS 后，以自己的 host capability生成 `status-sync-batch/2.0.0` 和 WDR command。meeting-sync另以自己的 capability写 Meeting Sync History。直接由 meeting/checkpoint/risk capability提交 current field MUST 返回 `WDR_WRITER_UNAUTHORIZED`。
- risk review直接拥有 risk-flow 与 decision fact；它不直接拥有 Dependencies 或 Cross-Workstream Links。该直接所有权只允许通过`owned-fact-command/1.0.0`进入普通fact fence：raw registry的`owned_fact_target_profiles`必须唯一匹配producer、operation、memory root、target path rule与content rule，capability必须授权`owned_facts`，且command的CAS、after raw bytes/hash与evidence必须逐项有效。profile不存在、重复、wrong producer/root/path/operation/schema、extra business target或stale generation一律在prepare前拒绝。checkpoint-sync直接拥有 Checkpoint Sync Log；workstream-register拥有 create；meeting-sync直接拥有 Meeting Sync History。所有共享 current-field变化仍经 status-sync。
- serialized `issuer`、command/proof中嵌入的capability object和其它wire graph字段都只是审计输入，MUST NOT授予权限。runtime在exclusive fact lock内从registry注册的capability-registry path加载canonical raw bytes，并由registry `runtime_authority_profile`选择native adapter：POSIX使用effective UID与已打开的运行中executable raw hash，Windows使用effective primary-token user SID、elevation/impersonation level与已打开的运行中executable raw hash；环境变量、wire字段或调用者字符串不得覆盖。adapter把effective identity先hash，再按profile的JCS算法导出principal ID，并产生只存在于调用栈的`runtime-authority-context/1.0.0`；context还绑定capability registry root/path/raw hash、exclusive fact lock profile/path、activation/attestation/capability epoch和adapter/executable identity。validator API必须把该context与raw capability bytes作为独立参数，拒绝从待验证graph构造、反序列化或回填它们；若wire graph同时携带registry副本，其bytes必须逐字节相等。engine以该外部authority验证active epoch、producer、operation及command实际出现的全部field/section；任一operation或field未获授权都在prepare前拒绝。capability registry恰好一条 active record per producer；`authorization_record_digest = SHA256(JCS(record excluding capability_id and authorization_record_digest))`，且`capability_id`必须逐字节等于该digest。任何只排除一个identity字段、两个identity不相等、内容重算不相等或duplicate producer/ID的record均拒绝。ID不是 bearer secret，queue bytes不授予权限，recovery和repair必须重新取得同一raw registry authority与native principal/epoch，不能从serialized repair graph重建权限。
- 本版本故意不定义capability create/rotate/revoke typed command。strict mode中任何runtime lifecycle请求 MUST 以`CAPABILITY_LIFECYCLE_REQUIRES_ROLLBACK`拒绝；操作员必须先通过registered activation transition回退legacy并递增activation epoch，使旧attestation立即失效，再在exclusive fact lock内执行reviewed bootstrap reprovision，随后full refresh与新attestation才可重启strict。实现不得用generic fact transaction、整文件替换或自定义command绕过此禁令。
- production evidence trust domain来自当前raw registry，当前registry MUST不预置任何production trust root。首次provision必须经过reviewed registry update，提供至少两个不同production roots，并遵守add-new-root、重签native evidence、再移除旧root的rotation顺序；root被移除、过期或泄露时implementation conformance立即回到`pending`。design fixture可在内存中的独立design-mock trust domain注入mock roots来测试acceptance算法，但这些roots和其receipt MUST NOT写入production registry、MUST NOT把production status改为`passed`，也MUST NOT授权strict publication。
- release acceptance、release-evidence transition、strict open、live inspect与strict publication都必须接收独立于候选receipt/release set/attestation/wire graph的host security context，恰为`{clock_source:"host-secure-clock-v1",evaluation_time:<canonical UTC>,available:true}`。`evaluation_time`由host可信时钟提供，不得取candidate `executed_at|signed_at|accepted_at|committed_at|inspected_at`作为authority；候选时间只做chronology约束。gate必须用该时间复验Python support-review deadline及production root的当前`not_before <= evaluation_time < not_after`，并要求release set `accepted_at <= evaluation_time`。时钟不可用时release acceptance/transition不得提交，live inspect返回`unverifiable/TRUSTED_CLOCK_UNAVAILABLE`，不得沿用上次green结果。
- meeting/checkpoint/risk producer command若产生current-field intent，command MUST携带其全部schema-valid `status_intents`原文；command fingerprint、journal manifest与fact proof因而绑定这些exact bytes。同一fact journal MUST把producer-owned business target与`mutation-intent-outbox/1.0.0`一起提交：outbox逐intent追加一条pending entry，entry的`intent`逐字节等于command中的canonical intent document，外层`intent_id = SHA256(JCS(intent))`，并绑定source command ID/fingerprint、origin producer、workstream和exact field set。不得从Meeting History文字、owned fact内容、producer名称或实现内置模板合成、替换或补全intent；command中的duplicate、hash mismatch、evidence/workstream不一致或outbox未逐项exact追加都使整个fact transaction在prepare前失败。
- meeting plan中的`status_intents`必须与`intent_outbox_commands[].status_intents`形成exact、去重、双向闭包；carrier的`source_instance_id`必须等于meeting instance，origin producer、workstream、evidence与canonical intent bytes必须逐项相等。即使没有Meeting History或其它producer-owned history target，plan只要存在intent就MUST生成至少一个`producer-intent-outbox-command/1.0.0`，以独立fact transaction持久化outbox；零history不能成为丢intent的理由。risk review的所有registry-authorized owned-fact profile，包括risk-flow和decision surfaces，只要`owned-fact-command/1.0.0`携带`status_intents`就都是合法carrier并必须在同一fact transaction exact追加outbox；profile名称不得改变presence-driven emission语义。
- outbox entry状态只允许`pending|consumed`。本版本不定义`processing|failed|waived` mutation或authority；convergence verdict中的`failed_intent_ids|waived_intent_ids`必须为空。任一pending intent都阻断Panel `fresh/eligible`，只有全部entries均由schema-valid committed fact receipt消费、verdict为`converged`时才可发布；实现不得通过自写terminal状态绕过status-sync。
- status-sync聚合WDR patch MUST携带按UTF-8排序的完整`consumed_intent_ids`，每个值都是该patch所消费exact intent document的JCS hash；该集合必须逐项等于`status-sync-batch/2.0.0`中绑定到此command的全部accepted intents，不能使用一个代表intent。fact transaction在同一outbox before image中查找全部ID，要求每项仍为pending、同workstream且exact intent bytes/hash/fields/evidence匹配；它原样保留所有无关prefix/rows，并把完整selected set原子转为consumed、共同绑定本次fact receipt。missing、extra、duplicate、already-terminal、cross-workstream或只消费子集一律返回`INTENT_OUTBOX_INVALID`；business bytes与outbox target通过同一journal roll forward/rollback，crash/retry不得留下“WDR已更新但部分intent仍pending”的状态。
- `status-sync-batch/2.0.0`的accepted intents按`(workstream_id,intent_id)`排序，`accepted_intent_ids`必须恰等于其去重ID集合；每个intent必须恰有一个binding，binding fields必须恰等于intent `set` keys，且只可绑定同workstream的status-sync授权WDR patch。accepted intent的workstream集合必须与WDR patch的workstream集合完全相等，每个workstream MUST恰好一条聚合patch；把同workstream intents拆到两条patch或遗漏空字段intent均返回`STATUS_INTENT_APPLICATION_INVALID`。绑定到同一command的字段按intent顺序合并：第一次赋值胜出，后续相同字段只有JCS bytes逐字节相等才可合并，否则整个batch在执行前返回`STATUS_INTENT_APPLICATION_INVALID`；evidence按JCS bytes去重排序。最终patch `set`和evidence必须分别恰等于该command绑定intent的merged fields与evidence union，不得漏、增或替换。action commands按`command_id`排序，WDR patches按`(workstream_id,command_id)`排序，`command_order`必须恰等于前者后接后者的ID序列，execution policy必须为`ordered-stop-on-first-failure-no-rollback`。
- batch不是跨command原子事务。executor按`command_order`逐个重新预检并提交独立fact transaction；首个prepare/apply/commit失败即停止，失败command及其后command不提交，较早已committed command保持committed且MUST NOT补偿回滚。恢复时按command ID+fingerprint查询durable fact receipt index：第一个没有matching committed receipt的command就是唯一retry cursor；retry从当前facts重读CAS/evidence后从该command开始，已committed前缀只做幂等重放检查。因而“batch成功”只表示全部ordered receipts存在，不构造第二个run-level truth。

## 3. WDR create、migration 与 patch renderer

- WDR 是无 BOM UTF-8、LF、恰好一个尾随 LF。sidecar保存 exact fingerprint、WDR revision、file generation与lifecycle；legacy无sidecar时二者为0。counter由engine对实际before/after bytes重算：bytes完全相等的纯no-op不提交且两者都不递增；bytes变化时`file_generation += 1`；只有Identity/Project Status current signature（含ledger-backed Next actions）实际变化时`wdr_revision += 1`。history或其它owned-section-only变化因此只推进file generation；一个mixed command无论改变多少字段都最多各推进一次。duplicate owned section、duplicate meeting key或同key不同bytes均返回 `WDR_SCHEMA_AMBIGUOUS`。
- create command内嵌完整`create_input`。engine先验证 `workstream-create-input/1.0.0`、重算`input_id`并要求command/create-input的`workstream_id`相等，再对 pinned template做 literal substitution：每个已声明token必须至少出现一次，替换其全部出现位置，替换后不得残留 `{{...}}`。artifact rows按 `(artifact,path,baseline_status,notes)` UTF-8 tuple排序；depends/impacts/L0去重排序；空列表渲染 `- TBD`；Markdown table cell先转义 `\\` 再转义 `|`；list item转义 leading marker；所有标量已由 schema拒绝换行。`Created`只来自 input的 canonical UTC timestamp。engine从command本身重渲染并验证template hash、rendered exact bytes/hash后，在同一fact transaction以`create`原子提交WDR、`delivery-record.state.json`和schema-valid空`action-projection.json`；三者的WDR revision/file generation均为`1/1`，sidecar actions为空。不得产生一个没有action sidecar、因而无法进入physical inventory的新WDR，也不得读取out-of-band logical input。
- create模板只强制 `Identity`、`BMM Artifact Index`、`Scope`、`Acceptance`、`Project Status`、`Cross-Workstream Links`、`Decisions and Evidence`、`Record Rule`；`Roadmap`、`Checkpoint Sync Log`、`Meeting Sync History` 在 create 时可缺。canonical total order是 Identity、BMM Artifact Index、Scope、Acceptance、Project Status、Roadmap、Cross-Workstream Links、Decisions and Evidence、Checkpoint Sync Log、Meeting Sync History、Record Rule；缺失optional section仍是该序列的合法subsequence。
- first target-state patch执行一次 byte-preserving grammar migration：legacy Roadmap无论位于何处都整体移动到 Project Status 与 Cross-Workstream Links之间；位于 Record Rule之后的 Checkpoint Sync Log整体移动到 Decisions and Evidence之后；legacy顶层 Meeting Sync Update整体迁入 Meeting Sync History。section body bytes及内部顺序不变，section之间规范为一个空行。重复heading、无法识别边界或跨section内容返回 `WDR_SCHEMA_AMBIGUOUS`。
- scalar/collection item做 NFC、trim ASCII SP/HTAB、拒绝 CR/LF/NUL。collection `replace/add/remove` 按 payload first-seen去重，保存已有顺序，`; `分隔，先转义反斜杠再转义分号。裸值`TBD`唯一表示空集合；真实collection item字面量`TBD`必须编码为`\\TBD`并可无损往返，不能被解析为空。缺 `Last status sync` 时固定插在 `Next actions` 后；其它 required label缺失阻断。缺目标optional section时按canonical total order插入。只替换目标label行或目标section，其它bytes不变。任何修改current signature的command若携带evidence，其最大`observed_at`不得早于现有`Last status sync`，且写入的`last_status_sync`必须精确等于该最大值；否则prepare前拒绝。
- Meeting Sync History条目key为 `(observed_at,entry_id)`，按 UTF-8 tuple排序。一个outer WDR command可以追加多个分别以该tuple为key的row，但每个`meeting_history_append` row的inner `command_id` MUST逐字节等于enclosing WDR command的outer `command_id`；任一不等均在fact attribution时拒绝。每块固定为 marker、H3、空行、Source/Classification/Update/Owner/Due / trigger/Status六行和两个尾随 LF；region紧邻 Record Rule。相同key相同bytes幂等，相同key不同bytes阻断。
- Roadmap只能由status-sync使用typed `roadmap:{mode:"replace",lines:[...]}`修改；`owned_sections`中的`section=roadmap`对status-sync不授权。`lines`至少两行、每行NFC且无CR/LF/NUL，并拒绝以`##` heading开头；renderer固定输出`## Roadmap\n\n`、按输入顺序以单个LF连接全部lines、section末尾无额外空行，外层section join再提供恰好两个LF。相同lines替换为no-op；任何其它mode或heading injection在prepare前拒绝。其它`owned_sections`也采用同一replace framing；append固定把现有section `rstrip("\n")` 后加一个LF再接lines，空lines、heading injection和跨section内容均拒绝。每个允许owned section都必须有byte-exact replace、append与replay-no-op conformance。

## 4. Ledger、action projection 与 fact fence

- action ledger v2固定pinned preamble，随后固定21列：`Action ID|Status|Owner|Workstream|Affected Workstreams|Action|Source|Reason|Due / Trigger|Closure Criteria|Closure Criteria Verifiable|Created At|Started At|Done At|Cancelled At|Baseline Revision|Related Plan Items|Related Flow Edges|Last Updated|Owning Workflow|Action Revision`。header、21个`---` separator、rows均使用`| `与` |`exact framing；文档无BOM、仅LF且恰好一个尾随LF。每cell必须是非空NFC单行；无值写`-`。renderer先把`\`转`\\`再把`|`转`\|`；parser只接受这两种escape并要求parse后重渲染与raw bytes相等。Affected Workstreams为空写`-`，否则按NFC UTF-8去重排序并用`, `连接；rows按Action ID的UTF-8 bytes排序且ID唯一。migration adapter可读取pinned 12列template或当前20列brownfield header，把缺失metadata/空cell规范成`-`、保留已有20列值并把缺失Action Revision设为1；首次mutation在shared fact lock内写回完整21列，不得删除Created/Started/Done/Cancelled、Baseline或关联字段。
- create row全部由command确定：command中的owner/status/action/due/closure/routing/affected原样应用；affected canonical排序；Source是evidence按JCS排序后的`source_path@source_fingerprint`以`; `连接；Reason=`command_id`；Created At=min(observed_at)，Last Updated=max(observed_at)，Owning Workflow=`adp-status-sync`，Action Revision=1；Closure Criteria Verifiable、Baseline Revision与两个Related字段默认为`-`。`in-progress|blocked|done`的Started At默认为Last Updated，`done`的Done At、`cancelled`的Cancelled At默认为Last Updated，其它lifecycle timestamp为`-`。
- patch先要求exact action ID唯一且Action Revision=`expected_revision`，只替换`set`中实际出现的owner/status/action/due/closure/routing/affected字段；omitted字段及全部非command metadata保持不变。before row和after row都必须满足`Created At <= Started/Done/Cancelled At <= Last Updated`，且同时存在时`Started At <= Done/Cancelled At`；status与允许出现的lifecycle timestamps必须一致。当前evidence的最大`observed_at`不得早于before `Last Updated`，防止旧会议覆盖新状态。`done|cancelled`为terminal，显式改成其它status必须在prepare前拒绝。合法status transition的timestamp规则固定：转`open`清空Started/Done/Cancelled为`-`；转`in-progress|blocked`在Started为空时写Last Updated并清空terminal timestamps；转`done`在Started为空时补Last Updated、Done=Last Updated、Cancelled=`-`；转`cancelled`保留已有Started、Done=`-`、Cancelled=Last Updated。每个patch将Source/Reason/Last Updated/Owning Workflow更新为当前evidence/command/status-sync，Action Revision恰加1；无论字段数，ledger revision恰加1。
- `action-ledger-state/1.0.0`从exact ledger bytes确定性生成：ledger fingerprint取raw SHA-256，actions按ID保存revision与exact rendered-row-plus-LF hash，applied commands按command ID保存command fingerprint/action ID，最后对不含`state_id`的完整JCS求identity。`action-flow-index/1.0.0`保留已部署的brownfield relation shape，顶层恰为`action_flow_schema_version="1.0.0"|actions|compatibility`，没有`contract`、ledger revision或`index_id`；compatibility固定`preserve-unmapped|ADP-ACTION-FLOW-MIGRATION-REQUIRED`。每个可投影ledger row按Action ID排序，只输出`action_id,status,created_at,updated_at,started_at,done_at,cancelled_at,baseline_revision,related_plan_item_ids,related_flow_edge_ids,source`；source固定指向`ACTION-LEDGER|actions/action-ledger.md`并绑定raw ledger fingerprint。baseline revision不是正整数、relation ID语法非法或lifecycle chronology非法的row按brownfield兼容规则不进入flow，但仍留在ledger并通过audit fail-visible；relation IDs按`,`或`;`解析、去重并按UTF-8排序。validator必须从before raw ledger执行上述create/patch、重渲染exact after ledger并重建state和此brownfield flow；owner/status/text/due/closure/routing/affected任一after-image回绑、omitted-field reset、terminal reopen或state/flow不一致均返回`FACT_ATTRIBUTION_INVALID`。routing/affected只属于ledger state/WDR action projection和drift计算，不得塞入action-flow v1。
- 每个action command的business target集合恰好是registry runtime path指定的ledger Markdown、`action-ledger-state/1.0.0`和`action-flow-index/1.0.0`三项，且三者root/path/operation/CAS完全由command推导；少一项、多一项或替换成其它business target均拒绝。action transaction不直接写WDR；若需要更新Next actions，上层只在action commit后发出独立、有序且有自己fact generation/CAS/receipt的`refresh_actions` WDR command。相同 command ID+fingerprint重放返回既有 action ID，same ID不同fingerprint阻断。
- action marker exact grammar为 `^\[action_id:([A-Z][A-Z0-9]*(?:-[A-Z0-9]+)+)\] <owner>: <action> \(due: <due>\)$`。owner/action/due使用RFC 3986 percent encoding：UTF-8 bytes、uppercase hex、space保留为ASCII SP，仅unreserved与SP不转义；解析后必须重新编码并逐字节等于原summary。manual entry保留原序，managed entry按 action ID排序；`refresh_actions`只替换managed entries并完整保留manual entries。marker不在entry开头、malformed/非canonical encoding或同action ID重复均阻断refresh与repair。
- fact-transaction-coordinator 是 receipt唯一writer；一个fact transaction只绑定一个schema-valid typed command，authorization fingerprint、capability scope和receipt delta从该command确定性导出，multi-command业务批次必须拆成有序transaction并由上层batch关联。journal与receipt都必须携带同一`authorizationRecordRef`：active capability registry ID、去除identity字段后重算的authorization record digest、command canonical fingerprint及producer/capability/epoch/principal。`fact-mutation-proof/1.0.0`另逐business target携带exact root/path/operation和base64 before/after raw bytes；validator必须先重算每个byte preimage的SHA-256并与journal target CAS相等，再解析WDR/JSON state并验证command-derived after state，不能只比较producer提供的hash。validator重算registry、record、command、proof、journal和receipt identity并要求逐字段相等。每个action delta固定exact action ID、operation、before/after revision、changed fields及evidence fingerprints；create为`null -> 1`，patch必须`after=before+1`。只刷新WDR ledger projection的`refresh_actions`不修改ledger action revision，receipt的`action_deltas`必须为空。fact generation必须恰好`before+1`，且schema-valid before/after `fact-generation-state`完整bytes分别绑定journal target的before/after hash，after state的transaction ID必须等于journal transaction。receipt business/generation targets与journal对应role完全相等，receipt target path/hash也必须与registry runtime path和receipt bytes相等。ledger、WDR、baseline/L0/kickoff、daily、meeting archive/cursor/receipt、decision、checkpoint candidate、raw readiness、capability/nonce state、action/risk indexes的任何 commit必须在shared fact lock中journaled并递增 `fact-generation.json`。strict mode禁止任何 owner workflow绕过coordinator。
- `owned-fact-command/1.0.0` transaction恰有一个business target，target root固定`memory`，path和create/patch operation从唯一registry profile导出；create要求before absent与`expected_before_sha256=null`，patch要求exact before raw hash，after bytes必须与command base64/hash逐字节一致并通过profile固定的JSON schema或canonical Markdown规则。proof/journal/receipt随后复用普通fact attribution、runtime authority、fact-generation和recovery规则；owned-fact receipt不得伪造action delta。risk-flow JSON必须是其pinned source schema的canonical bytes；workstream decision、decision log与business decision packet只能写profile允许的canonical Markdown path。exact retry幂等，same command ID不同fingerprint、额外target或restart后authority/generation变化均拒绝。

## 5. Projection profile、payload 与 publication

- `(root_instance_id,path)` 是唯一physical leaf key；同一key出现不同category、source kind或其它metadata必须返回`DEPENDENCY_IDENTITY_CONFLICT`，不得把这些metadata加入identity后并存。path必须是 NFC POSIX relative identity并拒绝 symlink/reparse point、case alias、colon、backslash、dot segment。enumerator从已验证root逐段遍历：exact path必须存在；selected workstream/sidecar/file按catalog selection展开；`previous_program_status_id=null`时immutable snapshot枚举为空；glob支持`**`零层或多层递归、排除hidden entry与symlink/reparse point、结果NFC后按UTF-8排序，unreadable/alias/normalization collision一律fail closed。leaf bytes只读一次并生成 fingerprint/blob。producer在instrumented resolver内只能读取 registry profile枚举的blobs和same-generation predecessor handles；actual read set必须与resolved allowed set完全相等，undeclared或declared-but-unconsumed均阻断。
- state-audit source projection不读取mutable current views；legacy view检查移到post-publication live inspect。`views/acceptance-readiness.md`与`views/cutover-readiness.md`也是派生输出，禁止作为roadmap/meeting-pack leaf；二者从selected WDR/evidence/decision/readiness/L0 raw facts和same-generation state-audit直接形成readiness board。Management Panel不得dereference upstream payload中的live path；source preview是schema-valid`{path,fingerprint,content}`数组，由upstream envelope携带immutable bytes。这样Panel profile只有renderer assets和same-generation upstreams。
- refresh output、canonical current views、`views/lineage/**`和`.adp-runtime/**`永不成为同轮leaf。previous program status只通过content ID解析immutable snapshot。action/risk flow在refresh前作为fact-generation-bound leaf index冻结。
- `action-projection.json`是status-sync在fact transaction中写入的sidecar，不是refresh projection。普通与repair `refresh_actions`都必须在shared fact lock内额外读取registry固定的ledger与ledger-state exact bytes，把两项作为proof `read_artifacts`按path顺序携带；validator解析完整21列ledger、重建ledger state并要求raw fingerprint/revision/applied commands相等。command `action_snapshot`必须恰等于active status `open|in-progress|blocked`且`routing_scope_id==workstream_id OR workstream_id in affected_workstreams`的全部rows，按action ID排序；snapshot每行逐字段携带ID、owner、action、due、status、action revision、routing、affected及exact rendered summary。sidecar after的ledger fingerprint/revision/actions必须逐字节等于该snapshot；ledger read bytes、fingerprint、revision、routing/affected membership或action set任一变化都拒绝提交。
- drift producer的profile必须直接枚举ledger、ledger state、WDR、WDR state和sidecar。对每个selected workstream先按同一规则重建expected snapshot，并把每个差异编码为`driftFindingV1`：sidecar ledger fingerprint/revision不同产生对应non-repairable finding；expected-only action产生`action-projection-drift/missing-from-wdr`，sidecar-only action产生`action-projection-drift/orphan-in-wdr`，共有ID的完整record不等产生`action-projection-drift/content-mismatch`；sidecar WDR revision/file generation与WDR state不等产生non-repairable `wdr-lineage-mismatch`，WDR parsed Next actions不逐项等于sidecar summaries产生non-repairable `wdr-content-mismatch`。每项正文包含repairability/severity/workstream、nullable action ID/diff及source位置，finding ID只按`SHA256(JCS(body))`生成；不得再使用literal action-suffixed ID。findings按ID的UTF-8序排列且不得重复；row没有finding才是`in-sync`，并携带exact WDR/sidecar fingerprints和lineage。verdict必须逐字节等于该算法输出并重算ID；selected IDs与rows恰好一行每selected ID，只有非空全覆盖且全部row为`in-sync`时overall才可`in-sync`，否则为`degraded`。空/缺/重复/额外rows、伪造finding/status或fingerprint不一致均不得发布。
- 每个 canonical output使用 `canonical-projection-envelope/1.0.0`，绑定 payload schema ID/raw hash、payload bytes hash、generation和instance key。registry的7个producer profile与7个`projection_payload_bindings`必须按projection kind一一对应：drift verdict、state-audit、program-status、roadmap、flow-graph、meeting-pack和Management Panel。每个binding显式声明schema path相对`document-workspace`或`project`；不得按进程cwd猜测。Program Status的`/progress`与`/flow_state`分别通过brownfield progress-v3与flow-state-v1完整schema；Management Panel v2是加法升级，必须在`model_v1`无损携带并分别通过pinned Panel model v1和manifest v1 nested binding，保留`project-lead|fde-morning|business-biweekly`三类view、scenario flows、history、selection/catalog/recovery、source/audit identities与keyed meeting boards。`model_v1`必须由同generation canonical payload的`extensions.panel_v1_source`加`sync.compatibility_inputs.{request,history,shareable_policy}`经pinned `panel_model.py`重新组合并逐字节等价；兼容corpus至少覆盖baseline、v2 current-field独立变化、program-status overlay变化和model tamper，不得从previous/current view沿用schema-valid旧模型。v2的`sync.canonical`并列携带全部canonical upstream payload，当前字段只读取`sync.canonical.status.workstream_current`，不得重写或缩减`model_v1`。producer必须先验证每个outer/nested binding、payload/envelope hash、manifest、receipt和same-generation predecessor linkage，再计算identity；unknown schema、hash/pointer mismatch、consumer pointer丢失或schema-invalid payload不得产生receipt。
- meeting packs一kind一实例。binding按RFC 6901；root source pointer是 `""`，key pointer `/scenario`，按meeting kind排序并 `object-by-key` 合并。duplicate/missing/unknown key阻断，绝不last-write-wins。
- 在shared read lock内，`physical-workstream-inventory-v1`必须先独立枚举`workstreams/*/delivery-record.md`，并要求每个visible one-level、NFC且符合wire `workstreamId`的目录都包含普通非symlink WDR与`action-projection.json`。enumerator必须验证完整WDR grammar/required labels、唯一Identity、sidecar完整registered contract、exact raw contract hashes及sidecar canonical JCS bytes；只检查两个identity字段不合格。hidden、nested、unreadable、unpaired、invalid content、duplicate normalized/physical identity和empty inventory全部拒绝。其attestation完整携带memory root ID、当前fact generation、按ID排序的全部workstream source rows、content-addressed inventory ID和重算attestation ID。selection policy同时携带与该attestation workstreams逐字节相等的`physical_workstream_inventory`及content-addressed `workstream_catalog`；policy不能自己缩小物理集合。`include_workstreams="all"`只在该双向闭包通过后从catalog解析；include/exclude未知ID、重复catalog ID或空结果都拒绝。generation必须逐字节绑定同一inventory/catalog identity及由registry `panel_binding_map`生成、schema-valid且重算ID一致的Panel catalog；generation中所有`selected-physical-wdr|wdr-action-sidecar` leaves与inventory必须双向完全相等，不得多、少或缺配对。
- `panel-publication-eligibility/1.0.0`独立于drift内部一致性，并且必须接收在本次publication检查期间重新枚举的fresh physical inventory attestation；不得复用policy内嵌inventory作为“独立检查”。attestation的contract/root/fact generation/content/inventory ID必须分别与loaded registry、generation root/fact generation及policy inventory/catalog逐字节一致。generation、audit、drift、Panel、全部manifest和receipt还必须携带同一个policy ID；audit selected scope、drift selected scope及canonical workstream ID集合必须与解析结果完全相等。只有artifact integrity pass、audit pass/ready、business freshness fresh、selected workstream恰好全覆盖且每行`in-sync`、overall也`in-sync`时，`publication_eligibility`才可为`eligible`。空scope、subset、额外行、任何drift/missing/malformed、blocked audit、freshness/eligibility不一致或stale/missing attestation都返回`PANEL_PUBLICATION_INELIGIBLE`；schema-valid但不可发布的payload不得进入current pointer。
- `panel-binding-semantics/1.0.0`从profile与selection独立推导exact instance cardinality：除meeting-pack外每个kind恰好一个null instance，meeting-pack恰好每个selected meeting kind一个。validator逐条解析registry binding，只接受同generation upstream envelope；`one`直接替换，`one-per-meeting-kind`按key pointer形成无重复object-by-key，并要求Panel target与解析值逐字节相等。missing/extra producer、instance、merge key或same-generation value mismatch均在Panel identity与publication前拒绝。
- v2 current-field browser边界由pinned `management-panel-v2-current-consumer/1.0.0`执行。它通过instrumented RFC 6901 resolver的actual read sequence必须恰好是primary data `/sync/canonical/status/workstream_current`，随后是trusted identity `/panel_id`；read set必须与registry `source_pointers`集合完全相等，且任何`/model_v1`或其后代读取都拒绝。consumer必须拒绝missing/non-NFC/duplicate或normalized-collision row，生成schema-valid `management-panel-current-view/2.0.0`与确定性escaped HTML。known-answer corpus必须保持legacy model byte不变而只修改progress/blockers/risks并证明可见HTML变化，也必须证明HTML metacharacter被转义且legacy-only变化不影响current view。
- Program Status不得只证明“读取过WDR”。`program-status-current-from-wdr/1.0.0`要求selected workstream为非空NFC UTF-8唯一排序集合，WDR bytes与WDR-state maps的key恰等于该集合。每个state必须schema-valid、active、path=`workstreams/<id>/delivery-record.md`且record fingerprint等于exact WDR bytes；parser要求完整WDR grammar和唯一labels，并从Identity读取phase/status，从Project Status读取progress及escaped blockers/risks/dependencies，从Next actions提取canonical managed action IDs。payload `workstream_current`必须按selected顺序逐行、逐字段恰等于这些值加state的fingerprint/WDR revision/file generation；carry-forward、漏行、额外行、旧lineage或WDR-only改变未传播一律返回`PROGRAM_STATUS_WDR_INVALID`。
- registry DAG必须展开为`(projection_kind,instance_key)`节点，并把每个resolved physical leaf identity作为source node。任一leaf或projection instance identity变化后，orchestrator按topological order重算direct input map并传播新identity，实际invalidated instance集合必须逐项等于direct加transitive闭包。一个meeting-pack实例变化只能失效Panel而不能污染其sibling；program-status或共享leaf可以同时失效两个meeting实例；只停在direct successor一层必须拒绝。
- publication前在shared fact read lock内重算全部leaves并复验fact generation、selection、catalog、producer receipts、payload schema、drift verdict与publication eligibility；再持锁取得panel publication lock，以panel generation CAS把所有canonical projections、Panel、pointer、panel state及publication receipt放入一个journal。source变化返回 `SOURCE_CHANGED_DURING_REFRESH`，Panel CAS冲突返回 `PANEL_GENERATION_CONFLICT`。
- 同generation的`state-audit|program-status|roadmap|meeting-pack|management-panel` payload、refresh receipt及任何其它携带`source_as_of`的document，其值 MUST逐字节等于selection policy的`as_of`；不得使用refresh完成时间、当前时间或max mtime。publisher在identity计算前执行全量相等检查，任一偏差返回`SOURCE_AS_OF_MISMATCH`。
- Panel publication graph必须显式携带schema-valid before/after current pointer与panel state；四个identity都重算，pointer/state target的before/after hash分别等于完整document bytes。pointer、state、panel receipt target path必须逐字节等于registry `runtime_paths`，receipt中的before generation/pointer ID、after generation/pointer ID、transaction/journal与这些documents和journal targets双向相等；redirect path或substituted preimage一律拒绝。
- 首次publication是唯一允许before pointer与before panel state同时absent的分支：两项必须同时为null，两个journal target必须为`create`且before hash/image为null，receipt固定`before_panel_generation=0,before_pointer_id=null`，after state固定`panel_generation=1`并绑定新pointer。后续publication必须同时存在两个schema-valid before document，两个target为`replace`，after generation恰为before+1。只缺一项、用generation-0 synthetic pointer、首次replace、后续create或混用分支都拒绝；每个apply边界的fresh-process recovery、roll-forward/rollback及幂等receipt replay使用同一journal规则。

## 6. Refresh run、status 与 live inspect

- producer receipt是discriminated union：produced/reused必须有output且error null；blocked必须output null且有typed error。不得为planned/blocked node伪造ID。
- immutable `refresh-run-receipt/1.0.0`逐instance记录 disposition、invalidation reasons、optional output、error和唯一retry cursor；dirty/blocked run保持completed outputs但不发布Panel。mutable `panel-refresh-status/1.0.0`只记录current run、last success、pending invalidations和latest inspect，不进入generation identity或Panel publication manifest。
- live inspect是restart-safe的完整解析，不接受调用进程缓存。registry把它显式注册为`strict-writer-fence-activation/1.0.0`的composition，scope必须包含strict validator及其完整传递输入；dispatcher实际authority/read set必须与该闭包相等。inspect在shared fact read lock内从raw registry解析runtime paths，读取strict activation state、当前writer-fence attestation、raw capability registry、durable release-evidence set及其每份receipt/blob raw bytes、current pointer、published generation lineage index、每个immutable lineage object、canonical envelopes/manifests/receipts/payload及live fact state，并按published generation/profile重新枚举leaves。每个lineage object必须与registry和generation派生的expected descriptor在kind、contract、root、path、instance和cardinality上exact全量相等；missing、extra、redirected或metadata substitution都返回`migration-required`。只有activation mode/epoch/state binding、attestation identity、capability epoch/bytes、accepted production receipt/blob集合、authoritative writer build/fence bytes、pointer/generation、lineage descriptor闭包、fact generation、root、selection、payload/manifest/receipt和leaf fingerprint全部相等时才可输出`fresh`。activation rollback或epoch mismatch、attestation replacement、capability epoch drift、writer bytes变化、raw registry仍为`pending`、只存在design evidence或任一strict closure不完整都返回`migration-required`；源内容变化但migration closure仍有效返回`stale`。它只更新registry固定的`state/panel-refresh-status.json`，不改业务facts；离线或权限不足必须`unverifiable`，不得报告fresh。
- inspect的trusted `evaluation_time`必须逐字节等于其schema-valid `inspected_at`，但authority仍来自独立host context；这条相等只把评估结果绑定到inspect receipt，不能让document反向提供时钟。inspect必须通过instrumented dispatcher证明actual root/path/contract read set恰等于registry `live_inspect_read_profile`闭包，且唯一写路径为`state/panel-refresh-status.json`；root registry、ledger、任一WDR/sidecar、latest refresh/publication receipt、extra writer read、lineage root-instance/cardinality substitution都不能被自洽metadata掩盖。

## 7. Journal、durability 与 recovery

- coordinator private locks/staging root固定 `.adp-runtime/panel-sync/1.0.0/`，但durable facts/views/receipts全部是registry `runtime_paths`相对memory root的逻辑路径，不得把private root前缀写入pointer。generation token固定`sha256:<64 lowercase hex> -> h_<hex>`；transaction ID、projection kind和非null instance key均为`i_ + lowercase SHA-256(UTF-8 NFC id)`，null instance固定`singleton`。因此canonical envelope路径只可为`views/generations/{generation_token}/projections/{projection_kind_token}/{instance_token}.json`，Management Panel只可为`views/generations/{generation_token}/management-panel/{instance_token}.json`；pointer=`views/management-panel/current-pointer.json`、panel state=`state/panel-generation.json`，fact/panel/repair receipt与journal路径逐字节来自registry。token输入拒绝empty、CR/LF、non-NFC；resolved path拒绝absolute、colon、backslash、empty/dot segment、unresolved token和alias。
- 每个transaction的journal目录必须精确为registry `journal_dir_template`解析的 `state/transactions/{filesystem-token(transaction_id)}`。manifest、prepared marker、terminal marker、recovery receipt、before/after images及remove tombstone分别只能使用registry的`journal_manifest_template|journal_prepared_marker_template|journal_terminal_marker_template|journal_recovery_receipt_template|journal_before_image_template|journal_after_image_template|journal_tombstone_template`；目录枚举发现unknown或重复这些对象一律corrupt。prepared manifest显式携带前四个resolved path，每个target固定role、operation、apply order、target before/after hash，以及before/after image locator；locator路径必须逐字节等于registered image template，包含parent alias、仅suffix相同或指向其它journal都拒绝。remove tombstone由transaction token+apply order确定，不接受调用者路径。locator含root ID和hash；create的before image/null，remove的after image/null，replace两者皆有。`transaction-journal-semantics/1.0.0`重算manifest/marker identity，按transaction kind强制完整role集合：fact为`business+fact-generation+fact-command-index+optional intent-outbox+1 fact receipt`；panel为`projection+panel+lineage-object+lineage-index+pointer+panel-state+1 panel receipt`；repair业务事务为`business+fact-generation+fact-command-index+nonce+1 fact receipt`；独立的repair-attempt事务恰为`repair-attempt-ledger+repair-index+1 repair receipt`。repair业务事务不得写repair receipt/index/attempt ledger，repair-attempt事务不得重写business、fact generation、command index或nonce。targets按apply_order从0连续、physical target identity唯一，receipt paths必须逐项等于role=receipt targets。terminal marker只允许`committed|rolled-back`并必须逐字段绑定journal/manifest；`committed`证明成功，`rolled-back`只证明已恢复before状态，`prepared`不能作为终态证据。
- apply按order执行，全部after后才写registered terminal marker。无terminal marker且all-after时roll forward；混合时逆序恢复全部before；unknown bytes报corrupt。有terminal marker必须all-after。recovery receipt写registered journal-local path且不属于原target。
- 原语包括 `durable_create`、`durable_replace`、`durable_remove_to_tombstone`。remove先原子rename到journal tombstone并flush双方parent，commit marker durable前不得删除tombstone；rollback从tombstone恢复。POSIX使用no-follow open/linkat/renameat+file/directory fsync；Windows使用CREATE_NEW、ReplaceFileW、same-volume MoveFileExW(MOVEFILE_WRITE_THROUGH)、FlushFileBuffers并拒绝reparse point。capability probe不能证明目标volume时返回 `DURABILITY_UNAVAILABLE`。

## 8. Per-batch repair

- drift producer与state-audit MUST共用`driftFindingV1`：正文固定为`kind|repairability|severity|workstream_id|nullable action_id|nullable action_diff|source_path|nullable source_line`，`finding_id = SHA256(JCS(body))`。action-level missing/orphan/content diff为`repairable/blocked`并携带完整typed action diff；ledger fingerprint/revision及WDR lineage/content类finding为`non-repairable/warning`、action字段为null，但仍必须进入verdict与audit，不得在canonicalization时删除。state-audit MUST消费已验证drift verdict的exact raw findings，以相同finding ID映射workflow/workstream/operation、entity refs、action IDs与nullable batch；不得另造literal ID或第二种hash。finding全局唯一，sort key是 `(workflow,workstream_id,operation,finding_id)`，group key只有前三项；同group形成一个batch，每个repairable finding恰好属于一个batch，双向 `repair_batch_id`必须匹配；`repair_batch_id=null`只表示当前不进入自动repair，不得删除该finding或其entity identity。`repair-graph-semantics/1.0.0`以dry-run request中的batch ID从audit精确查找目标（不得取数组首项），并分支验证完整wire graph：dry-run blocked只能有audit/request/result/blocked receipt且无token、business journal、attempt journal或fact receipt；applicable后必须形成`unused -> reserved -> consumed|invalidated` nonce链。committed先以repair业务journal原子提交business targets、fact generation、fact-command index、final nonce和fact receipt，再以独立repair-attempt journal原子追加attempt ledger与repair receipt index并创建repair receipt；rolled-back先以business journal的rolled-back marker和journal-local recovery receipt证明恢复before、令`fact_receipt_id=null`，再由独立且committed的repair-attempt journal持久化invalidated终态及repair receipt。每个分支都递归验证exact contract refs并重算batch digest/ID、dry-run ID、binding digest、token hash/nonce ID、两个journal及所有receipt/state identity；validator不得接受out-of-band preimage或`binding_input`。
- 每个finding中`entity_type=action`的`entity_refs[].id`序列必须无重复、已NFC canonical排序并逐项等于该finding的`action_ids`；finding action ID union、command action IDs和read-set action IDs也必须完全相等。missing、extra、duplicate、normalized collision或只修改其中一种表示都返回`REPAIR_BATCH_INVALID`。每action恰好一个read record：存在时 `expected_present=true, revision>=1`；ledger完全不存在时 `expected_present=false,revision=null`，absence仍由ledger fingerprint保护。WDR read-set恰好一条；source `(root,path)`唯一。任何duplicate same/conflicting identity都返回 `REPAIR_BATCH_INVALID`。
- dry-run必须在fact lock内从registry路径打开exact ledger、ledger-state、WDR、WDR-state与sidecar raw bytes；先验证canonical ledger-state与ledger bytes/fingerprint一致，再从实际ledger row逐action推导`expected_present/revision`，从同一WDR/sidecar snapshot重算typed drift findings并要求与输入verdict逐字节一致。read-set不得自行声明presence、revision或action diff；absent-claim/present-row、present-claim/absent-row、wrong revision、invented diff、drift receipt/generation substitution均在签token前返回`REPAIR_BATCH_INVALID`。这些exact read bytes/hashes同时进入fact proof，repair后的WDR/state/sidecar必须由同一ledger snapshot推导。
- dry-run/result/token/apply/receipt均一batch。client按batch ID排序；首个失败停止，已提交batch不回滚，失败batch重新读取audit/facts并签发新token。两批partial retry必须以三个完整wire graph执行证明：A以token A完成business与attempt两次commit并保留；B以token B在stale CAS后写`reserved -> invalidated`、business rolled-back marker和recovery receipt，再commit其attempt journal；进程restart后通过registered repair receipt index与attempt ledger跳过已有matching committed receipt的A，从当前facts重新dry-run B、取得不同token并以rebound expected revision/read set完成两次commit。只比较plan或伪造status transition不构成conformance。每次dry-run/apply和restart后的retry都必须取得与普通fact mutation相同的独立runtime-authority context与raw capability-registry bytes。binding只从schema-valid wire documents重建，精确包含roots、principal/scopes、当前schema/registry raw hashes、audit ID、batch ID/digest、完整read set和outcome。`issued_at <= applied_at <= expires_at <= issued_at+15m`，超期或延长均拒绝。nonce ID是token hash，path必须逐字节等于registry `repair_nonce_template`以nonce filesystem token解析的结果；三个持久态必须以`previous_state_id`形成`unused->reserved->consumed|invalidated`，reserved/final绑定同一principal、business transaction和binding。business journal的nonce target before/after hash必须分别等于reserved/final bytes；fact receipt必须精确绑定business journal的business/fact-generation targets及batch action/revision集合。
- business terminal marker durable后，attempt identity不得由实现自由选择：用`B={business_transaction_id,business_journal_id,business_marker_id,business_marker_sha256,recovery_receipt_id,recovery_receipt_sha256}`，其中两个raw hash必须从registry路径实际加载的canonical marker/optional recovery receipt bytes计算；`D=SHA256(JCS(B))`，`attempt_transaction_id="repair-attempt:" + hex(D)`，`attempt_journal_id="journal-repair-attempt:" + hex(D)`，journal目录再由registered transaction token规则解析。repair receipt、attempt ledger entry与repair index entry MUST逐项携带相同`B`和两个attempt IDs；attempt与business transaction/journal ID必须不同。attempt ledger与repair receipt index只允许append一个共享连续sequence的exact entry，并绑定business terminal state及repair receipt的ID/path/raw hash。repair-attempt journal的三个target hash必须分别匹配attempt ledger、index与repair receipt bytes，其terminal marker必须committed。进程必须能在business marker之后及三个attempt target的每个边界崩溃，仅从registered manifest/marker/image/receipt paths重新推导同一attempt ID并幂等roll forward到唯一sequence与receipt；不得重跑已terminal的business transaction或追加第二次attempt。
- `refresh_actions` repair只重写目标WDR的Next actions、WDR state与`action-projection.json` sidecar，business targets必须精确为这三项；它不修改action ledger或action revision，因此fact receipt必须`action_deltas=[]`。committed repair不得自行构造hash-shaped authorization：它必须携带active capability registry、typed WDR command、before/after fact state及fact mutation proof，并先通过与普通WDR mutation完全相同的`fact-receipt-attribution/1.0.0`，再验证batch/nonce/repair receipt。proof中的WDR before bytes必须匹配repair read-set fingerprint，after sidecar ledger fingerprint/action IDs必须匹配batch read set/command。orphan action read使用`expected_present=false,revision=null`，仍由ledger fingerprint和WDR CAS保护。

## 9. Migration 与 evidence gate

- rollout固定：runtime/coordinator；action v2+ledger state+legacy adapters；shared WDR engine/sidecars；全部fact writers；projection envelopes/profile read instrumentation；atomic publication；live inspect/drift；repair。部署仍是现有local CLI/file模式，不引入service/provider。strict mode只能在raw registry `implementation_conformance_status=passed`且`state/strict-activation.json`为`strict`、当前activation epoch存在完整writer-fence migration attestation时启用；producer提供的status副本不具authority。release gate先把accepted receipts及其全部evidence blobs写入registry固定content-addressed paths，再原子发布`release-evidence-set/1.0.0`到`state/release-evidence/current.json`；set逐项绑定result ID、receipt/blob path与raw hash，目录枚举发现unindexed/extra/missing bytes均拒绝，trust-domain必须与当前registry一致。attestation的`binding_scope`固定为`immutable-writer-fence`：它只授权当前root registry、capability registry与epoch、release evidence authority，以及每个authoritative writer的build/fence/capability coverage；它不把activation时的fact generation、ledger/WDR bytes、refresh/publication receipt、pointer、lineage或Panel generation冻结成后续mutation的授权前像。schema中保留的这些snapshot字段仅作迁移诊断，不参与strict authorization、open freshness或publication equality
